# 月度收支环比与账户余额环比

## 一、接口变化

### 1. 月度收支

`GET /api/v1/transactions/monthly-statistics/?month=2026-11`

`month`仍为可选参数，格式`YYYY-MM`；不传时使用当前月份。
原有`current_month`、`previous_month`、`current`、`previous`及百分比字段保留。

`data.comparison`示例：

```json
{
  "income_rate": "29.50",
  "expense_rate": "-26.67",
  "income_change_amount": "1180.00",
  "expense_change_amount": "-400.00",
  "income_trend": "up",
  "expense_trend": "down"
}
```

收入、支出按所选自然月的正常账单合计，与上一个完整自然月比较。
不按同期天数折算；未来日期但归属所选月份的已录入正常账单也会计入。
`current.balance`仍然是月收入减月支出的结余，不是账户余额。

### 2. 账户净余额

以下两个接口均新增`data.asset_comparison`：

- `GET /api/v1/dashboard/summary/`：当前实时净余额与上月末比较。
- `GET /api/v1/transactions/monthly-statistics/?month=YYYY-MM`：账户部分同样返回当前实时净余额与实际上月末的比较；`month`仅影响收支统计。

例如实际为11月，选择10月时，总收入、总支出比较10月与9月；账户余额仍为当前值，与10月末余额比较。
因此顶层`current_month`可能为`2026-10`，而`asset_comparison.current_month`为`2026-11`，这是两种统计口径，前端不能强制要求月份一致。
账户余额卡片建议标注“当前账户余额”，金额读取`asset_comparison.current_net_assets`，不要根据所选月份隐藏余额。

```json
{
  "current_month": "2026-11",
  "previous_month": "2026-10",
  "previous_net_assets": "25000.00",
  "current_net_assets": "28653.00",
  "change_amount": "3653.00",
  "change_rate": "14.61",
  "trend": "up",
  "has_previous_snapshot": true,
  "has_current_data": true
}
```

只统计当前用户未删除、已启用的账户，与原首页口径一致。
正余额计入资产，负余额绝对值计入负债；净余额为总资产减总负债。
停用、重新启用账户会影响统计范围，因此也参与快照结转保护。

## 二、百分比与方向

百分比为`(本期金额 - 上期金额) / 上期金额 × 100`，保留两位小数。

| 状态 | 含义 | 前端建议 |
|---|---|---|
| `up` | 增加 | 较上月增加百分比；百分比为空则显示增加金额 |
| `down` | 减少 | 较上月减少百分比的绝对值；为空则显示减少金额的绝对值 |
| `unchanged` | 持平 | 较上月持平 |
| `new` | 上期为零、本期为正 | 较上月新增金额 |
| `unknown` | 缺少当前月或上月资产数据 | 暂无历史对比数据 |

- 上期为零或负数时，百分比为`null`，不返回虚构的100%。
- 两期都是零时，方向为`unchanged`，百分比仍为`null`。
- 无快照时，历史余额、变化金额、百分比为`null`，不把缺失历史当成零。
- 两个公开接口的资产部分都使用当前实时余额，正常查询时`has_current_data=true`，即使选择历史收支月份也不隐藏当前余额。
- 没有上月快照时，当前余额仍正常显示；只有环比提示“暂无上月末数据”。
- 金额差额保留正负号，显示“减少”时前端取绝对值。
- 很小的变化可能四舍五入为`0.00%`，方向仍按实际金额判断，可优先展示变化金额。

## 三、快照生成规则

新增表：`user_asset_monthly_snapshot`，同一用户、同一月份只能有一条记录。

1. 首次访问、账户变更或执行结转命令时，只建立当月未结转记录。
2. 未结转记录是跟踪起点，不能当作已经确认的月末余额。
3. 跨月后，先锁定用户，在任何账户变更前读取余额，确认上个月月末快照。
4. 若连续多个已跟踪月份没有账户变化，可以将同一余额逐月结转。
5. 已结转快照不再覆盖；事后补记、修改历史账单影响当前实际余额，不改写已确认月末快照。
6. 按系统实际执行时间跟踪余额，而不是按账单填写的发生时间反推历史。
7. 新增、修改、停用、删除账户、余额校准、转账及撤销、账单增删改恢复均在余额变更前接入结转。
8. 结转和余额业务处于同一事务。业务失败，结转也一起回滚。

上线前没有跟踪过的月份不补造。例如11月首次启用，10月余额返回无数据；跨入12月后可获得11月末余额。
直接SQL、脚本批量更新账户或绕过业务Service写入，不受上述变更入口保护；这类操作需要另外接入同一结转流程。

## 四、本地启用

本次生成迁移文件，不自动迁移已有开发或服务器数据库。
在项目目录中执行：

```powershell
python manage.py migrate
python manage.py close_asset_snapshots
```

第二条命令为所有现有用户建立跟踪起点，并结转已经跟踪的历史月份。
它不会创建虚假的上线前历史，也不会修改账户余额。

只处理一个用户：

```powershell
python manage.py close_asset_snapshots --user-id 1
```

## 五、Ubuntu Docker更新

本次有新增数据库表，更新时必须迁移。
建议在短维护窗口暂停后端写入，防止旧镜像中的业务绕过新的跨月保护。
先完成代码拉取、镜像构建和数据库备份，再在`/opt/bookkeeping`依次执行：

```bash
sudo docker compose stop backend
sudo docker compose run --rm --no-deps backend python manage.py migrate --noinput
sudo docker compose run --rm --no-deps backend python manage.py close_asset_snapshots
sudo docker compose up -d --no-deps backend
sudo docker compose exec nginx nginx -t
sudo docker compose exec nginx nginx -s reload
```

任何运行旧后端代码的周期账单任务、脚本或本地开发服务也应暂停，更新后再恢复。
迁移前运行新代码会因快照表不存在而报错；每条命令成功后再执行下一条。

## 六、计划任务

应用内读取首页、月度统计或执行账户变更时已经会自动结转。
仍建议每天运行一次批量结转，便于无访问用户及时建档、结转。

在Ubuntu创建日志目录：

```bash
mkdir -p /opt/bookkeeping/logs
```

使用`sudo crontab -e`配置root计划任务，示例：

```cron
5 0 * * * cd /opt/bookkeeping && /usr/bin/docker compose exec -T backend python manage.py close_asset_snapshots >> /opt/bookkeeping/logs/asset-snapshots.log 2>&1
```

请按实际Docker路径、部署目录和宿主机时区调整。命令内部月份以Django配置时区为准。
重复执行不会重复建立月末快照；虚拟机关机期间不会执行计划任务，下次业务访问或命令调用时结转已跟踪的无变化月份。
