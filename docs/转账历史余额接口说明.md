# 转账历史余额接口说明

## 一、返回字段

以下接口复用转账序列化器，均增加四个历史余额字段和一个完整性标记：

- `POST /api/v1/accounts/transfers/`：创建转账成功后返回本次快照。
- `GET /api/v1/accounts/transfers/`：列表中每条记录返回自身快照。
- `GET /api/v1/accounts/transfers/{id}/`：详情中返回该笔转账快照。

原有请求参数、响应字段和查询权限规则不变。

| 字段 | 类型 | 含义 |
|---|---|---|
| `source_balance_before` | 金额字符串或null | 转出账户转账前余额 |
| `source_balance_after` | 金额字符串或null | 转出账户转账后余额，已扣除金额和手续费 |
| `target_balance_before` | 金额字符串或null | 转入账户转账前余额 |
| `target_balance_after` | 金额字符串或null | 转入账户转账后余额，增加转账金额 |
| `has_balance_snapshot` | boolean | 四个历史余额是否完整；真实零余额也视为有效数据 |

例如从余额1000元的账户向余额200元的账户转账100元，手续费2元，新增返回：

```json
{
  "source_balance_before": "1000.00",
  "source_balance_after": "898.00",
  "target_balance_before": "200.00",
  "target_balance_after": "300.00",
  "has_balance_snapshot": true
}
```

金额统一保留两位小数；信用卡负余额保留负号。

## 二、历史口径

1. 这四个字段就是该笔转账对应的历史余额，读取时不查询账户当前余额替代。
2. 在两个账户加锁后，扣款前记录before，扣款入账后记录after，与转账记录同事务落库。
3. 后续收入、支出、转账、余额校准不会改变原转账的快照。
4. 撤销转账会恢复资金并修改原状态，但不覆盖原快照。详情是否允许查询撤销记录沿用原接口规则。
5. 余额对应本次操作实际执行时点，可参考`created_at`，不是按用户填写的`transfer_time`反推。
6. 旧记录未保存过历史余额，新增列保持NULL，`has_balance_snapshot=false`。无法仅凭当前余额可靠还原过去。
7. 同一幂等请求重试返回第一次的响应，不重复扣款、不重新生成快照；升级前已有的幂等缓存仍回放原响应。
8. 前端不能提交或修改这些只读字段，余额全部由后端计算。

本次返回的是单笔转账的前后余额，不新增账户全量余额流水接口。

## 三、前端展示

现有Vue项目已预留四个同名字段，详情页可直接读取。
有快照时显示转账前后余额，并校验：

```text
转出后余额 - 转出前余额 = -(amount + fee)
转入后余额 - 转入前余额 = amount
```

旧记录缺失时保留“暂无历史余额”，不要显示0或用当前账户余额倒推。

## 四、启用和部署

新增迁移：`apps/accounts/migrations/0004_transfer_source_balance_after_and_more.py`。
本次仅生成迁移，不自动修改已有MySQL数据。

本地在虚拟环境、项目目录中执行：

```powershell
python manage.py migrate accounts
```

成功后重新启动后端。未迁移就访问转账接口会因缺少新列而报错。
本迁移不需要重新执行资产跟踪初始化命令，也不会补造历史余额。

Ubuntu先同步代码、构建镜像并备份数据库，再在`/opt/bookkeeping`运行：

```bash
sudo docker compose stop backend
sudo docker compose run --rm --no-deps backend python manage.py migrate accounts --noinput
sudo docker compose up -d --no-deps backend
sudo docker compose exec nginx nginx -t
sudo docker compose exec nginx nginx -s reload
```

每条命令成功后再执行下一条；对外服务尚未部署本次修改，需要更新镜像才生效。
